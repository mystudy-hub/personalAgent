**目标版本：** V1.0 MVP  
**文档修订：** 2026-11-26  
**项目类型：** 本地优先、多 Agent 协作的个人智能体系统  
**运行环境：** Windows 11 本地控制服务，专用 WSL2 发行版承载首版 Worker<br>

# 第一章：项目背景与建设目标

## 1.1 项目背景

随着大语言模型、Agent 工具调用和自动化开发技术的发展，传统单 Agent 模式逐渐暴露出一些问题：

1. 对话和任务执行混在一起，职责不清晰。
2. 不同任务共享上下文，容易产生记忆污染。
3. 一个 Agent 同时承担规划、执行、审查等工作，复杂度过高。
4. 长时间运行的任务容易阻塞用户交互。
5. 多个项目之间缺乏统一的知识管理和任务管理。
6. 自动执行涉及文件、代码、命令和外部服务时，缺少统一的安全控制。

因此，需要建设一套个人智能体系统，将聊天、任务调度、任务执行、长期记忆和权限管理进行解耦。

系统不以简单增加 Agent 数量为目标，而是建立一套能够长期运行、持续积累知识、管理项目并执行复杂任务的个人工作平台。

## 1.2 建设目标

建设一个以本地计算机为核心运行环境的 Personal Agent 系统，实现以下能力：

| 能力 | 建设目标 |
|---|---|
| 独立聊天 | 拥有独立人格和长期用户记忆 |
| 任务调度 | 能理解需求、拆分任务、分配执行角色 |
| 多 Agent 协作 | 多个专业 Worker 并行完成工作 |
| 长期记忆 | 统一管理用户、项目和执行记忆 |
| 项目管理 | 能理解多个 GitHub 项目的结构和进度 |
| 自动开发 | 调用 Codex 完成代码开发、测试和审查 |
| 异步执行 | 长时间任务不阻塞聊天 |
| 安全控制 | 高危操作必须经过权限检查 |
| 可观测性 | 能查看任务状态、执行日志和资源消耗 |

## 1.3 核心设计原则

### 原则一：交互与执行分离

聊天 Agent 负责与用户交流。

主 Agent 负责理解和调度任务。

Worker 负责执行具体工作。

不能让一个 Agent 同时承担全部职责。

### 原则二：Agent 不等于业务系统

Agent 负责理解、推理和决策。

任务管理服务负责任务状态。

数据库负责持久化。

工具网关负责权限。

不能将系统的可靠性完全建立在提示词约束之上。

### 原则三：记忆统一管理

所有 Agent 使用统一的记忆服务，但根据角色获得不同的记忆视图。

避免每个 Agent 独立维护一套互不相通的长期记忆。

### 原则四：先实现可靠性，再实现自主性

第一阶段不追求完全自主运行。

优先保证：

- 任务能够正确创建。
- 任务能够稳定执行。
- 任务能够中断和恢复。
- 执行过程能够追踪。
- 重要操作能够审批。
- 失败后能够定位原因。

# 第二章：总体系统架构

## 2.1 架构设计

系统采用七层架构。

1. 用户交互层
2. Agent 角色层
3. 任务编排层
4. Worker 执行层
5. 记忆管理层
6. 工具与安全层
7. 数据持久化与监控层

V1.0 的一条开发任务按以下顺序运行。各角色按授权向 Memory Gateway 读取上下文。系统自己执行的工具操作逐次经 Tool Gateway 校验，Codex 步骤在网关准备的隔离边界内运行（见 6.6）。Task Manager 将每次状态变化写入 SQLite。

```text
聊天中心 → Chat Agent → 用户提交任务草稿 ─┐
任务中心直接提交 ──────────────────────┴→ Task Manager 创建任务
                         ↓
            Main 填写模板参数 → 编排器实例化并校验节点
                         ↓
           Research → Coding（隔离工作区）→ Review
                         ↓
          审批中心展示候选 diff → 用户决定 → 工具网关复核并创建交付分支
                         ↓
          Task Manager 记录结果 → Main 汇总报告 → Chat 展示
                         ↓
              Memory Gateway 保存已验证的项目结论
```

图中的 Worker 顺序用于 CSV 验收。普通问答可直接返回，只读任务可在审查完成后交付。

## 2.2 模块职责

| 模块 | 主要职责 | 是否独立运行 |
|---|---|---|
| Chat Agent | 日常交流、人格管理、记忆查询 | 是 |
| Main Agent | 任务理解、规划、调度 | 是 |
| Task Manager | 任务创建、状态管理、重试 | 是 |
| Worker Runtime | 执行具体任务 | 是 |
| Memory Gateway | 记忆检索、写入和权限控制 | 是 |
| Tool Gateway | 统一工具调用和权限检查 | 是 |
| HITL | 高危操作审批 | 作为独立服务或模块 |
| Monitor | 日志、事件和运行状态 | 是 |

说明：这里的独立运行指逻辑和生命周期独立，不要求第一版全部部署为独立进程。

## 2.3 第一版架构约束

为了避免初期过度设计，V1.0 采用模块化单体架构。

即：

- 一个本地后台服务。
- 多个独立 Agent 配置。
- 多个可并发执行的 Worker。
- 一个统一数据库。
- 一套统一工具权限机制。

后续根据实际负载，将任务调度、Worker 和记忆服务拆分为独立进程。

# 第三章：Agent 角色体系

## 3.1 Chat Agent：聊天智能体

### 定位

负责所有日常交流，是用户与 Personal Agent 系统之间的主要沟通入口。

### 主要职责

1. 日常问答。
2. 用户需求理解。
3. 用户长期偏好管理。
4. 项目背景查询。
5. 任务进度查询。
6. 将复杂需求转交 Main Agent。
7. 将执行结果转换为用户容易理解的语言。

### 配置文件

```text
agents/chat/
├── soul.md
└── agent.md
```

`soul.md` 负责：

- 人格。
- 语言风格。
- 交流方式。
- 行为原则。

`agent.md` 负责：

- 工作流程。
- 记忆调用方式。
- 任务转交规则。
- 工具调用限制。

权限和可用工具不放在 Agent 目录内，由 `config/permissions.yaml` 和 `config/tools.yaml` 按角色统一定义（见第八章）。

### 权限要求

日常对话可查询任务和经授权的记忆摘要。用户明确要求保存、更正或撤回自己的偏好时，Chat 可向记忆网关提交仅限本人偏好的请求；网关鉴权、写入版本并返回回执。项目事实由第五章的写入流程维护。Chat 的工具权限排除 Shell、代码修改和文件删除。

## 3.2 Main Agent：主调度智能体

### 定位

系统的任务决策中心。

### 主要职责

1. 接收用户任务。
2. 分析任务目标。
3. 识别任务类型。
4. 查询项目记忆。
5. 制定执行计划。
6. 拆分子任务。
7. 分配 Worker。
8. 监控执行进度。
9. 处理异常。
10. 汇总执行结果。

### 任务分类

| 任务类型 | 默认 Worker |
|---|---|
| 软件开发 | Coding Worker |
| 技术研究 | Research Worker |
| 数据处理（后续） | Data Worker |
| 代码审查 | Review Worker |
| 策略研究（后续） | Quant Worker |
| 系统运维（后续候选） | DevOps Worker |

### 调度规则

普通问答由 Chat 直接答复，不创建任务。

V1.0 的 CSV 修复任务由 Main 填写项目、输入和验收条件，编排器据此实例化固定的 Research → Coding → Review 模板。不匹配模板的任务进入 BLOCKED，显示支持的任务类型。

第二个实际场景出现后，再评估模型生成依赖图及跨领域子任务并行。

涉及重要文件和外部系统变更的任务，必须经过工具权限检查。

## 3.3 Worker 专业角色

V1.0 注册 Coding、Research 和 Review 三种 Worker。Data 与 Quant 的职责保留供后续版本使用。

### Coding Worker

职责：

- 代码编写。
- Bug 修复。
- 模块重构。
- 单元测试。
- 技术实现。

执行工具：Codex。

### Research Worker

职责：

- 技术调研。
- 官方文档分析。
- 技术方案对比。
- 项目可行性分析。
- 技术报告生成。

### Data Worker

职责：

- 数据采集。
- 数据清洗。
- 数据格式转换。
- 数据质量检查。
- 数据库分析。

### Quant Worker

职责：

- 期货策略研究。
- 行情分析。
- 策略参数研究。
- 回测结果分析。
- 风险指标分析。

### Review Worker

职责：

- 代码审查。
- 逻辑漏洞检查。
- 安全性审查。
- 测试结果验证。
- 交付质量检查。

注意：第一版 Worker 应当是专业角色配置，不必为每个角色建立独立模型或独立服务。可以复用同一个模型运行环境，通过不同配置和权限实现职责隔离。

## 3.4 Worker 标准工作流程

所有 Worker 遵循统一协议：

```text
接收任务
   |
读取任务上下文
   |
检查执行权限
   |
执行任务
   |
生成执行结果
   |
运行验证
   |
提交结果
   |
等待运行时验证与审查
```

Worker 不得自行修改任务目标。

如果发现需求不明确、权限不足或执行条件不满足，必须返回阻塞状态，而不是自行猜测。

# 第四章：任务管理与调度系统

这是整个系统的核心基础设施。

不能只依赖 Main Agent 的上下文来维护任务状态。

## 4.1 任务生命周期和恢复规则

Task Manager 是状态的唯一写入者。下表中的动作由对应角色发起，经 Task Manager 校验后落库。状态、事件、版本号及当前执行尝试在同一事务更新。父任务汇总必需子任务的结果并等待自己的验收条件满足，部分成功需在报告中列出。

| 当前状态与触发 | 条件或动作 | 结果 |
|---|---|---|
| 用户提交草稿 | 按项目和提交幂等键创建任务；重复请求返回原任务 ID | `CREATED` |
| `CREATED` 开始规划 | Main 读取本任务允许的上下文 | `PLANNING` |
| `PLANNING` 收到计划 | 编排器校验角色、输入输出、无环依赖和权限；失败规则见 7.3 | 合法进入 `READY`，需补充条件进入 `BLOCKED` |
| `READY` 调度器领取 | 依赖均已成功、容量允许，原子领取并记录租约与尝试 ID | `RUNNING` |
| `RUNNING` 交付候选产物 | 运行时记录来源和产物版本，生成实际 diff 和测试证据（见 6.4） | `REVIEWING` |
| `REVIEWING` 完成审查 | 只读结果验收通过可交付；需修改则附原因退回 Coding，退回轮数达到配置上限时转由用户处理；批准交付前展示审过的版本 | 分别进入 `SUCCEEDED`、`READY`（达到上限为 `BLOCKED`）或 `WAITING_APPROVAL` |
| `WAITING_APPROVAL` 收到决定 | 有效批准后进入分支交付步骤；用户可附意见退回 Coding 或拒绝并终止该次交付；退回关闭原审批，计入该任务的退回轮数；过期或基线变化须重新核对 | 批准进入 `RUNNING`，退回进入 `READY`（达到上限进入 `BLOCKED`），拒绝进入 `CANCELLED`，失效进入 `BLOCKED` |
| `RUNNING` 完成已授权分支交付 | 网关回读分支引用并记录回执；必要步骤全部通过 | `SUCCEEDED` |
| 可执行步骤遇到故障 | 可安全重试则在配置上限内新建尝试；条件缺失或副作用不明记录核对项；确定失败且重试耗尽则保留证据 | `READY`、`BLOCKED` 或 `FAILED`；规划阶段重试回到 `PLANNING` |
| 执行时长达到上限，或下一次宿主模型调用、Codex 尝试将超出各自额度 | 停止后续调度，按取消的规则终止正在执行的尝试，保留已有产物和证据 | `BLOCKED`，等待用户处理 |
| `BLOCKED` 条件解除 | 保存解除原因，按检查点回到规划、审查、审批或执行队列；产生新 diff 须重审 | `PLANNING`、`REVIEWING`、`WAITING_APPROVAL` 或 `READY` |
| 用户请求暂停或继续 | 尚未领取的步骤立即暂停；正在执行的步骤先保存请求，在安全边界落检查点。继续时重新检查依赖、基线和审批有效期 | `PAUSED` 并保存恢复位置；继续后从相应检查点调度。终态优先于迟到的暂停请求 |
| 用户取消非终态任务 | 停止后续调度，撤销尚未消费的批准，通知执行器终止。先核对已经开始的外部操作 | 可确认停止后进入 `CANCELLED`，结果不明进入 `BLOCKED`；核对后若取消仍有效则进入 `CANCELLED` |
| 服务重启或租约过期 | 读取最后的检查点、操作回执和待审批记录；旧租约的 Worker 无权再提交结果 | 等待审批、暂停状态保留；安全步骤重新排队；外部写入结果不明进入 `BLOCKED` |

**取消与完成竞争。** 状态更新须匹配当前版本和执行尝试。已提交的成功结果保留，晚到的取消返回实际终态；先被接受的取消阻止后续步骤。若写入已发生，在报告中记录实际改动和取消时点。终态保存为历史，人工重新发起时关联原任务。

**核对外部写入。** 创建分支前持久化操作 ID、目标仓库与分支、基线提交和获批候选提交。恢复时回读该分支。指向获批提交则补记回执；分支缺失、原操作仍可继续且批准和基线有效时，可用同一操作重试；指向其他提交或结果无法判定时阻塞，展示实际结果。推送仍按独立操作核对。

**终止与恢复。** 每次尝试用独立目录和受控进程组。取消、超时或服务异常退出后，先终止并确认该尝试的进程组已清空，再生成证据、释放目录或重试。无法确认时阻塞任务并保留该目录。

## 4.2 数据模型

4.1 的状态属于任务。计划中的每一步是节点，节点的每次执行是一次尝试。其他章节所说的子任务即节点，父任务即节点所属的任务。

| 对象 | 关键字段 | 状态与规则 |
|---|---|---|
| 任务 | `task_id`（如 `TASK-2026-000001`）、项目、提交幂等键、标题与目标、类型、优先级、截止时间、约束、版本号、暂停或取消请求、关联的原任务、时长、宿主模型请求与 Codex 尝试额度及各自累计用量、退回次数 | 4.1 的全部状态。由 Task Manager 依据节点、操作、审批的进展和用户请求写入 |
| 节点 | 节点 ID、所属任务、角色、输入、预期产物、依赖、验收条件 | 等待依赖、`READY`、`RUNNING`、`SUCCEEDED`、`FAILED`、`BLOCKED`、`CANCELLED`。V1.0 的检查点只设在节点边界 |
| 尝试 | 尝试 ID、所属节点、租约、起止时间、退出信息 | 每次重试或审查退回新建一条，旧尝试只读。只有持有当前租约的尝试能提交结果 |
| 产物 | 所属尝试、类型、内容摘要、存放位置、生成者 | 不可变。候选 diff、测试记录、审查结论和报告都是产物 |
| 操作 | 操作 ID、类型、目标仓库及分支、基线提交、候选提交、diff 摘要、回执 | 网关执行的每个有副作用的动作各一条，如创建交付分支、推送 |
| 审批 | 绑定的操作、任务、执行身份、目标仓库及分支、基线提交、候选提交及 diff 摘要，有效期，审批人、决定和时间 | 待决定、已批准、已退回、已拒绝、已过期、已撤销、已消费。一次批准只能消费一次 |
| 事件 | 递增序号、所属任务、类型、时间、引用的对象 | 只追加。界面按序号补读 |

**任务状态与节点的对应。** 任务为 `RUNNING` 时，有节点在执行，或有已批准的操作在执行。`REVIEWING` 表示 Review 节点正在审查当前候选或只读结果。`WAITING_APPROVAL` 表示有审批等待决定。审查退回时，Coding 节点回到 `READY` 并新建尝试，Review 节点在新候选交付后重新执行；原候选和原审查结论保留为历史。

**三类检查的分工。** 运行时验证产出事实，即实际 diff 的摘要和测试的退出码（见 6.4）。Review 在此之上给出判断，决定 `REVIEWING` 的去向。人工审批只针对改变用户项目或远端的操作。Main 负责计划和汇总报告，不承担验收。

## 4.3 任务拆解机制

首版模板及适用范围见 3.2。后续扩展到多个场景时，拆解计划遵循以下原则：

1. 明确最终目标。
2. 确定任务依赖关系。
3. 将任务拆成可独立执行的工作单元。
4. 确认每个子任务的输入和输出。
5. 识别可并行任务。
6. 识别必须串行执行的任务。
7. 确定最终验收条件。

后续量化场景的拆解示例：升级中国商品期货量化项目的数据模块。首版 CSV 验收的角色分工见第十五章。

```text
主任务
  |
  +-- 检查现有数据源
  |
  +-- 检查数据库结构
  |
  +-- 检查数据质量
  |
  +-- 制定改进方案
           |
           v
       Coding Worker
           |
           v
       Review Worker
```

# 第五章：统一记忆管理系统

## 5.1 设计目标

建立统一的记忆网关，避免不同 Agent 各自保存重复、冲突和过时的信息。

记忆系统应当解决：

1. 用户信息如何保存。
2. 项目知识如何保存。
3. 执行结果如何保存。
4. 记忆如何检索。
5. 记忆如何更新。
6. 记忆冲突如何处理。
7. 不同 Agent 如何获得不同记忆权限。

## 5.2 记忆分类

建议划分五种记忆。

| 类型 | 内容 | 示例 |
|---|---|---|
| User Memory | 用户长期偏好 | 使用 Windows、偏好技术方案先规划后实施 |
| Project Memory | 项目长期信息 | 项目架构、技术选型、开发进度 |
| Technical Memory | 技术知识 | 接口规范、设计方案、常见问题 |
| Execution Memory | 执行记录 | 任务结果、错误、测试报告 |
| Session Memory | 当前会话信息 | 当前需求和临时上下文 |

## 5.3 记忆存储结构

建议采用：

- SQLite：结构化记忆和元数据。
- Markdown：人类可读的项目知识。
- 首版先按授权项目和标签过滤，再用参数化 LIKE 匹配关键词子串，转义输入中的通配符。用两个汉字的关键词验证可召回项目内记录。后续可从已授权、未归档的记录重建向量索引。
- 原始文件：完整报告、日志和证据。

不建议第一版就建设复杂知识图谱。

先把记忆的分类、更新、检索和权限做好。

## 5.4 记忆网关接口

建议统一接口：

```text
POST /api/memory/search
POST /api/memory/write
POST /api/memory/update
POST /api/memory/archive
GET  /api/memory/{id}
GET  /api/memory/project/{project_id}
```

其中：

`search`：根据 Agent 身份和任务检索相关记忆。

`write`：写入新记忆。

`update`：更新已有记忆。

`archive`：归档过期记忆。

## 5.5 记忆写入规则

记忆写入必须具备：

- 来源。
- 创建时间。
- 适用项目。
- 可信度。
- 版本。
- 状态。
- 更新记录。

特别是项目记忆，需要明确区分：

- 已确认事实。
- 当前设计方案。
- 待验证假设。
- 已废弃方案。

不能将 Worker 的推测直接作为已确认事实保存。

## 5.6 记忆权限隔离与数据使用

| 数据 | 读取和写入规则 | 模型调用可用内容 |
|---|---|---|
| 会话与用户偏好 | 会话和版本记录保存在本机 SQLite。Chat 可读取本人授权摘要；用户明确表达保存、更正或撤回意图后，由网关写入、替代或归档相应版本 | 按本次用途提供相关偏好和必要的会话片段 |
| 项目记忆、源码和 diff | Main 限当前授权项目；Worker 限任务用途、项目和所需文件。经审查的事实必须带任务 ID、证据和来源，待验证内容单独标记 | 为项目配置允许的模型服务及数据类别，仅发授权片段；未配置源码或 diff 外发授权时，需该数据的远程步骤转为阻塞 |
| 测试、日志和附件 | 完整产物保存在本机，报告引用产物位置。先做项目范围过滤，再检索或排名 | 发送获准的错误摘要或测试摘录。凭证、令牌和命中的敏感字段在请求及应用日志中剔除 |

网关使用服务端确定的用户、项目和任务身份。窗口中打开的项目、模型生成的项目 ID、检索词均不授予访问权。相同数据边界适用于 Chat/Main 的模型请求以及 Codex 可读取的输入工作区。

**偏好验收。** 用户说“以后用中文回复”，Chat 提交偏好请求，收到网关回执后再确认保存。新会话读取生效版本。用户更正为“以后用英文回复”后，新会话使用更新值；撤回后归档的记录不参与默认检索。另一项目 Worker 仅能看到当前任务获准的内容。

# 第六章：工具执行与安全控制

## 6.1 统一工具网关

所有 Worker 不应直接无限制地调用系统资源。

统一工具网关负责：

1. 身份验证。
2. 工具权限检查。
3. 参数校验。
4. 操作风险分类。
5. 审批检查。
6. 执行记录。
7. 结果返回。

以上检查适用于系统自己执行的每一次工具操作。Codex 步骤内部的读写和命令不逐次经过网关，约束方式见 6.6。

## 6.2 工具分类

| 工具类型 | 示例 |
|---|---|
| 文件工具 | 读取、搜索、修改文件 |
| 开发工具 | Git、Python、Codex |
| 代码平台 | GitHub API |
| 网络工具 | HTTP、搜索接口 |
| 数据工具 | SQLite、CSV、行情接口 |
| 系统工具 | PowerShell、系统命令 |

## 6.3 权限分级

建议采用四级权限：

| 等级 | 类型 | 操作策略 |
|---|---|---|
| P0 | 只读 | 在本次授权项目和数据范围内允许 |
| P1 | 普通写入 | 按项目授权 |
| P2 | 重要变更 | 人工确认 |
| P3 | 高危操作 | 强制审批 |

典型操作：

| 操作 | 等级 |
|---|---|
| 读取项目文件 | P0 |
| 查询已注册 GitHub 仓库的元数据 | P0，仅网关使用只读凭据 |
| 创建临时文件 | P1 |
| 在隔离工作区生成候选补丁 | P1，限本任务 |
| 在隔离环境运行登记的基线和候选测试 | P1，限本次尝试 |
| 在用户仓库创建本地交付分支 | P2，批准具体候选提交及目标分支 |
| Git Push | P2 |
| 删除重要文件 | P3 |
| 修改系统配置 | P3 |
| 生产环境部署 | P3 |

## 6.4 HITL 人工审批机制

1. **准备输入。** 网关固定基线提交，导出独立的源码副本，按尝试分配隔离目录。测试命令及参数来自用户登记的项目配置。基线和候选均由运行时在隔离边界内执行同一登记命令。
2. **生成证据。** Coding 结束并确认进程组清空后，网关收集允许的文件，使用由网关保管的 Git 元数据生成候选提交及规范化 diff。运行时从该提交物化独立副本，隔离运行回归，记录命令、退出码和输出。失败基线与候选回归均绑定提交。示例仓库用受控的行尾规则保证物化可重现。
3. **审查候选。** Review 核对实际 diff、失败基线和候选回归，将结论绑定至候选提交与 diff 摘要。审批页单独标出测试文件和可改变执行行为的配置，包括 Codex、Agent 指令、Git 属性和 CI 配置。证据不足或测试失败时按 4.1 退回。
4. **批准与交付。** 审批展示目标仓库、新分支名、基线和候选提交、diff、测试证据及有效期。网关复核批准、登记的基线引用及目标分支，再将候选对象导入仓库并以“引用须不存在”为前置条件创建新分支。工作区、索引和当前分支由用户继续管理。候选变化须重审，审批绑定的目标或基线变化须重新批准。
5. **回读与报告。** 以实际分支引用和提交为准记录交付回执。用户自行合并；Git push 单独授权和核对。中断按 4.1 恢复。

## 6.5 审计日志

所有重要操作必须记录：

```text
操作时间
任务 ID
Agent ID
Worker ID
工具名称
经脱敏的操作参数、目标基线和候选摘要
审批记录
执行结果
错误信息
```

## 6.6 信任边界与强制机制

| 对象 | 信任程度 | 约束方式 |
|---|---|---|
| 后台服务自身的代码：Task Manager、编排器、网关、Worker Runtime | 可信 | 状态、审批和回执只由它写入 |
| 工作台界面 | 持有会话凭据时可信 | 本地接口认证，见下文 |
| 其他网页和本机其他进程 | 不可信 | 没有会话凭据的请求一律拒绝 |
| 各角色的模型输出 | 不可信 | 只作为待校验的请求。状态转换由 Task Manager 校验，工具操作由网关校验 |
| Codex 及其命令、运行时启动的项目测试 | 不可信 | 隔离边界加产物检查，见下文 |
| 仓库内容、网页和附件 | 不可信的数据 | 不授予任何权限，也不改变执行配置 |

**两种约束方式。** 创建交付分支、推送和 GitHub API 调用逐次经过工具网关。Codex 内置工具及其命令、运行时启动的项目测试均由隔离边界约束。运行时可收集产物和记录证据，执行项目代码的子进程使用隔离身份。

**隔离边界的要求。**

- 每次尝试使用独立源码副本。Git 元数据由网关在步骤不可达的位置保管。导出副本不带源仓库的 Git 配置、远端或 hooks。网关以自己的 Git 配置和元数据构造候选。
- 步骤的写入限尝试目录，读取限已获准输入。命令和测试进程的出站与回环访问均须受限，不能访问 PA API 或取得用户的 Git、Codex、模型服务和界面会话凭据。模型请求按 5.6 由获准的客户端或宿主适配器发起。
- Codex 使用独立、最小的配置根，并单独认证。排除用户和目标仓库自带的命令规则、技能、记忆、MCP、插件、hooks 和项目授权。M0 用空白夹具验证实际生效的配置及凭据边界。

**M3 Windows 与 WSL2 的边界。** Windows 端运行控制服务，掌握任务数据库、审批记录、用户仓库和 Git 引用写入。Worker 运行在专用 WSL2 发行版内，由服务显式选择发行版和非 root 用户，关闭宿主固定盘自动挂载与 Windows 互操作。发行版只配置 Worker 所需的运行时和独立模型认证。Codex 命令沙箱、项目测试隔离和命令侧网络限制仍按本节验收。

Windows 网关固定基线，以字节流交付独立源码副本并回收经校验的候选产物。该通道不暴露用户仓库路径、Git 元数据、审批凭据或任务数据库。候选提交、diff 和交付分支由 Windows 网关管理。导出与回收按 Git 基线内容验证字节和文件模式。验收包含启用 `core.autocrlf` 的 Windows 仓库，未修改的往返必须产生零 diff。

跨边界验收从实际部署的 Windows 服务身份发起。使用合成夹具确认该身份可启动指定发行版的非 root Worker，验证两条执行路径的隔离、字节往返，以及取消、超时和 Windows 启动器异常退出后整棵进程树清空。普通用户下进程命名空间与 Codex 命令沙箱的兼容性需要实测。无法确认清理时保留现场并阻塞任务。现有 M0 结果只覆盖 WSL2 内部样例；Windows MXC 保留为独立候选，按同一门禁验收后才可接入。

**本地接口与审批通道。**

- 服务只监听 127.0.0.1。
- 每次启动生成会话令牌。所有 HTTP 请求和实时连接都校验令牌，并校验 Origin 和 Host。
- 审批接口只接受界面会话的凭据，任何 Worker 身份都没有审批权限。

**M0 隔离门禁。** Claude 对本机当时配置下的 `codex sandbox` 记录显示，写限制生效，目录外读取、出站和回环未被拒绝。提权后端以及实际 `codex exec` 路径仍待验证。先用无真实数据的临时夹具评估 Windows 提权后端。验证隔离写入、未授权读取、命令出站、回环、凭据访问和远端写入边界，覆盖 Codex 子命令及运行时启动的测试命令。通过条件包括允许动作的正对照，以及所有禁止动作被拒绝。Windows 后端未通过时，评估专用 WSL2 环境，对宿主文件、互操作、网络、进程和凭据执行同样验收。门禁通过后才接入样例流水线。

**本机预检（2026-11-26）。** Windows 提权后端执行固定文本的启动检查时报 `registered Core launch requires an installed app`，尚未进入隔离验收。已确认 Ubuntu 22.04（WSL2）可启动，专用隔离环境仍待配置和验收。临时 Git 仓库已验证新引用创建、回读、同名冲突拒绝，以及当前分支、索引和工作区状态保持一致。

# 第七章：本地技术架构与选型

## 7.1 总体技术选型

第一版优先考虑稳定、成熟和易维护。

| 模块 | 建议技术 | 说明 |
|---|---|---|
| 开发环境 | Windows 11 | 本地运行 |
| Agent 开发 | Python | 业务逻辑和调度 |
| Agent 执行 | Codex | 代码开发和专业任务执行 |
| API 服务 | FastAPI | 提供统一接口 |
| 数据库 | SQLite | 任务和记忆元数据 |
| 文件存储 | Markdown / JSON | 人类可读知识 |
| 记忆检索 | SQLite 项目过滤、关键词和标签 | 向量检索列入后续版本 |
| 任务队列 | SQLite + asyncio | 初期异步调度 |
| 前端 | React + TypeScript | 任务工作台 |
| 实时通信 | HTTP 服务端推送事件（SSE） | 任务进度按事件序号推送。工作台使用携带会话令牌的 fetch 读取事件流，断线后携最后已处理的事件 ID 重连补读 |
| 日志 | Python logging | 运行日志 |
| 版本管理 | Git | 代码和配置管理 |

以上是建议选型，不是对现有环境已安装组件的确认。

## 7.2 Codex 集成

Codex 是整个系统重要的开发执行引擎。

建议采用独立适配层：

```text
Agent Runtime
      |
Codex Adapter
      |
Codex CLI / Supported Runtime
      |
任务隔离工作目录
```

Codex Adapter 负责：

- 启动执行任务。
- 传递任务描述。
- 指定工作目录。
- 配置执行权限。
- 获取运行状态。
- 收集执行结果。
- 处理中断和超时。

不应将 Codex 的内部配置与 Main Agent 的业务调度逻辑混在一起。

需要先验证当前 Codex 版本支持的调用方式、认证模式和权限参数。适配层固定经过验证的 Codex 版本、发行版和入口，升级时重新执行调用与隔离验收。Windows 服务从实际部署身份启动 WSL Worker，按 6.6 经标准输入输出传递任务和产物，并保留原始日志字节。Worker 在专用发行版内直接启动 Codex，使用独立配置根和按尝试回收的进程边界。Job Object 的验证适用于 Windows 原生候选。

首版直接使用 Codex 完成开发任务。出现第二种 Coding Agent 的实际需求时，再评估 ACP 客户端，验收其权限策略、取消和产物契约。OpenHands Canvas 与 Agent Server 的部署对照不列入首版路线。

## 7.3 对话、规划与执行的模型调用约定

| 调用者 | 输入与输出 | 失败时对用户可见的结果 |
|---|---|---|
| Chat | 使用已配置的模型适配器。输入限当前消息、必要历史及授权摘要；输出为普通答复或可编辑任务草稿。用户提交后由 Task Manager 分配任务 ID | 认证、配额或网络故障显示可重试原因；重复提交同一草稿返回同一任务 |
| Main | 通过与 Chat 相同的模型适配器提取模板参数。编排器生成节点 ID，从模板读取角色、依赖及预期产物，并校验输入与验收条件 | 编排器拒收改变模板节点或依赖、缺失验收条件和越权的参数。带原因返回 Main 修正一次；仍无效则进入 `BLOCKED`，界面展示节点及待补充项 |
| Worker | Research 由运行时读取授权文件，Review 由运行时读取候选与测试证据，两者通过 Chat 使用的模型适配器分析获准片段，仅返回发现或判断。Coding 使用 Codex CLI。正式 diff 和测试证据由运行时生成。每步记录尝试 ID 和执行结果 | 可重试故障受次数上限约束。权限或资料不足返回阻塞原因，错误及进程退出信息记入任务事件 |

M0 分别验证 Chat 的一次真实问答、Main 的一次 CSV 模板填参以及 Codex 的一次只读执行。模型提供方、模型名及认证方式由部署配置指定。M0 记录所选服务、四个模型角色（Chat、Main、Research、Review）的授权输入范围和一次认证验证结果；凭据只交给宿主适配器。Codex CLI 的认证另行验证。每次模型调用先执行 5.6 的数据检查。宿主在发出模型请求前原子预留一次额度，重试同样计数。Codex CLI 按尝试次数和墙钟时长设置硬上限，每次启动前预占一次额度，达到时限时按 4.1 终止进程。内部模型请求量在可观测时记录，计数依据保持独立。

### M1 任务底座实现

本机 FastAPI 支持 Git 项目注册、按项目和提交键去重的任务写入，以及按事件序号查询。SQLite 支持从首批数据库无损升级。Task Manager 在同一事务内更新任务、尝试和事件。模拟 Worker 领取两个可独立完成的步骤，每完成一步保存检查点。运行中暂停在当前步骤结束时生效，取消由 Worker 在轮询时确认。重启保留已暂停任务，已中断的任务在租约过期后从最后一个检查点领取。旧尝试无法提交结果。

在仓库根目录使用项目虚拟环境安装服务依赖，然后以本机回环地址启动服务。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:PA_SESSION_TOKEN = [Guid]::NewGuid().ToString("N")
.\.venv\Scripts\python.exe -B -m core.api
```

默认地址为 `http://127.0.0.1:8000`，数据库默认位于 `data/database/pa.sqlite3`。可用 `PA_PORT` 和 `PA_DB_PATH` 覆盖。模拟 Worker 默认启动两个，每步 0.75 秒，租约 5 秒。分别用 `PA_SIM_WORKERS`、`PA_SIM_STEP_SECONDS` 和 `PA_SIM_LEASE_SECONDS` 调整。

请求携带 `Authorization: Bearer <PA_SESSION_TOKEN>`。使用 `POST /projects` 登记 `name` 和绝对 Git 工作目录 `path`，随后用 `POST /tasks` 提交 `project_id`、`submission_key`、`title` 和 `goal`。用 `GET /tasks` 查看任务清单，向 `POST /tasks/{task_id}/pause`、`/resume` 或 `/cancel` 提交控制请求。客户端可用 `GET /tasks/{task_id}/events?after=0` 查询事件，并以最后收到的 `sequence` 继续补读。

在仓库根目录运行 `.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v`。集成测试启动临时回环服务，验证并行执行、暂停跨重启、过期尝试重领、检查点不重复和运行中取消。此阶段执行器使用固定模拟步骤；模型角色协议及审查流程属于 M2。

### M2 Agent 协作实现

`POST /chat/drafts` 接收项目、标题、目标和固定 CSV 模板参数，返回可编辑草稿及计划预览。用户提交草稿前，服务不会写入任务。向 `POST /tasks` 提交草稿时，服务重新校验参数，并生成和持久化 Research、Coding、Review 节点及其依赖。重复提交需匹配原任务参数。跨项目引用、超出模板的源文件以及自行提供节点或依赖均会被拒绝。

直接提交的模板参数由 `plan_parameters` 提供，包括当前 `project_id`、`template=csv_blank_line`、`source_file=csv_import.py` 和 `test=unittest`。

配置 `PA_MODEL_BASE_URL` 和 `PA_MODEL_NAME` 后，`POST /chat` 可以调用 Responses API。需要 Bearer 认证时从 `PA_MODEL_API_KEY` 读取。默认 `mode=answer` 返回答复，`mode=task` 携带已登记的 `project_id` 返回可编辑草稿。提交该草稿后，Main 获得用户确认的目标和项目 ID，并填充固定模板。校验未通过时最多纠正一次，仍无效则进入 `BLOCKED` 并保存原因。任务记录模型调用次数，重复提交沿用已有任务。

Chat 和 Main 的单次模型请求有 15 秒总时限，覆盖建立连接和读取流式响应，服务端心跳不会延长时限。断流或协议错误在 Chat 返回可读的模型错误，在 Main 记录为任务阻塞原因。Main 收到取消后先关闭在途模型请求，再结束尝试并释放 Worker。

Research、Coding 和 Review 通过模拟 Worker 生成按尝试绑定的产物。Review 核对候选标识、改动摘要和模拟运行时测试证据。证据不足时退回 Coding，达到 `PA_REVIEW_LIMIT` 后进入 `BLOCKED`，默认上限为 2 轮。审查通过后进入 `WAITING_APPROVAL`。用 `GET /tasks/{task_id}/summary` 查看状态、计划调用次数、退回轮数、阻塞原因和产物历史。真实仓库执行、审批和分支写入在 M3 接入。

6. 是否能执行未审批的危险命令。
7. 是否会被恶意任务内容诱导执行越权操作。
8. 未带会话凭据的请求、跨站请求和 Worker 身份能否调用审批接口。

第 2 项的判定标准见 6.6。

## 12.3 稳定性测试

测试：

- 后台任务运行数小时。
- Worker 异常退出。
- 服务重启。
- 数据库异常。
- 模型接口超时。
- 重复提交任务。
- 并发任务竞争。
- 审批过程中服务重启。

必须保证任务状态和执行记录不会因普通服务重启而丢失。下列场景用临时仓库和可控的模拟执行器复现；每次记录任务 ID、尝试 ID、事件序列、审批状态和目标仓库差异。

| 演练 | 注入时点 | 可复核的预期结果 |
|---|---|---|
| 暂停后恢复 | 正在运行的节点收到暂停，请求后重启服务 | 明确展示请求与生效时点；下一个节点未被领取；从已记录检查点继续，已完成步骤不重复 |
| 审查退回 | 候选测试失败或证据缺失 | 审查原因可见；新尝试产生新候选；仅新版本可被批准交付 |
| 取消与完成竞争 | 分别让完成、取消先取得任务版本 | 仅接受有效状态转换；晚到请求取得实际结果，无后续节点抢跑 |
| 审批期间重启 | 审批申请落库后、用户决定前 | 重启仍等待原请求；批准、拒绝、过期和重复请求有可追溯结果 |
| 分支创建后回执丢失 | 目标引用创建之后、成功回执入库之前 | 回读分支；指向已批准提交时补回执，指向其他提交时阻塞，引用缺失按 4.1 处理 |

# 第十五章：发布验收与后续综合场景

## 15.1 V1.0 发布验收：修复 CSV 导入空行

**前置条件。** 使用 PAT-6 的独立 Git 示例仓库。样例含表头、两条有效记录和中间的空白行。此处空白行指两条记录之间没有字符的空行。预期返回两条有效记录，同时保留无空行输入的既有行为。带分隔符的空字段和引号内跨行内容沿用原解析规则。运行时记录基线提交，并在其隔离副本上跑出修复前失败的测试。各验收场景使用同一基线的独立副本。

**样例复现。** 从本仓库根目录运行 `python -B scripts/init_csv_fixture.py D:/pa-csv-fixture`，可将示例创建在尚不存在且有写权限的目录中。脚本输出基线提交，样例 Git 仓库没有远端。进入样例目录后运行 `python -B -m unittest -v`。基线应恰有 1 项失败（空白行被解析成额外记录）和 3 项通过。一次性验证副本中的修复已通过全部 4 项，模板保留故障供端到端验收。

**M0 集成复现。** 在已配置 Codex 模型 API 的 WSL2 中，从本仓库根目录运行 `python3.11 -B scripts/verify_m0.py --exercise`。它使用临时仓库模拟批准与拒绝；去掉 `--exercise` 时由操作者输入候选提交决定批准，直接回车表示拒绝。运行 `python3.11 -B scripts/check_m0_worker_cleanup.py` 可独立复验真实 Worker 的取消、超时和启动器异常退出。

1. 用户在聊天中心输入“修复 CSV 导入遇到空行的问题，运行测试，给我看改动”。提交草稿后得到唯一任务 ID。
2. Main 填写 CSV 模板参数，编排器生成 Research → Coding → Review 节点。Research 定位导入逻辑、失败样例与证据；Coding 在隔离目录完成修改并运行测试；运行时按 6.4 生成实际 diff 和测试记录；Review 对同一候选版本核对 diff、失败基线和修复后测试。
3. 审批中心显示源项目、目标、基线、候选 diff 和测试证据。此时对照起始快照，用户仓库内容应一致。
4. 用户批准后，网关创建本地交付分支并回读引用。核对引用指向通过隔离回归的已批准提交，并确认交付前后的工作区、索引和当前分支一致。
5. 报告列出任务目标、原因、文件清单、测试命令及结果、未解决问题、审批决定、本地交付分支、实际提交与远端推送状态。Memory Gateway 将有证据的项目结论关联到任务；新会话可查回结论及来源。

| 单独重演的分支 | 通过条件 |
|---|---|
| 用户附意见退回 | 原审批关闭，目标仓库保持原状；新候选重新生成证据、审查并申请批准；达到轮数上限进入 BLOCKED |
| 用户拒绝或审批过期 | 目标仓库保持起始状态；拒绝记录或过期原因可查，候选 diff 留供查看 |
| 审批后候选或目标发生变化 | 原批准不能覆盖新内容；展示最新差异，候选变化须重审，基线变化后对重新核对的版本申请批准 |
| 同名交付分支已存在 | 该分支引用保持原值；若它来自本次操作且指向已批准提交，则按 4.1 补记回执；其他冲突进入阻塞 |
| 审批或写入中服务重启 | 按 12.3 留存恢复前后事件和仓库证据；无重复操作 |
| 未请求提交或推送 | 报告明确显示各操作的实际状态，不以候选产物或模型回复推断发布成功 |

# 第十六章：建设建议与最终决策

## 16.1 建设策略

建议采用：

**本地优先、单机部署、模块化架构、渐进式扩展。**

第一版不需要 Kubernetes、复杂微服务或大型消息队列。

重点是先打通：

用户交互 → 任务调度 → Worker 经工具网关生成候选 → 审查与批准 → 分支交付与报告 → 记忆更新。

## 16.2 建设优先级

1. 先通过 M0 隔离门禁，再验证模型入口和本机环境，建立可复现的 CSV 基线，用真实 Codex 在样例仓库的副本上走通一条写死的流水线。
2. 以这条流水线为依据交付能恢复的任务系统，实现角色协议和工具权限，在正式的审批流程可验证后接入真实 Codex 写入，完成首个端到端任务。
3. 将记忆权限、前端进度和报告接入同一任务记录，按第十五章验收发布。

## 16.3 最终建设目标

最终形成一个以用户为中心的本地 Personal Agent 系统：

- Chat Agent 是个人助手。
- Main Agent 是项目负责人。
- Worker 是专业执行团队。
- Memory Gateway 是长期知识库。
- Task Manager 是任务管理中心。
- Tool Gateway 是执行控制中心。
- HITL 是安全审批机制。

**核心理念：让 AI 不只是回答问题，而是能够理解长期目标、组织专业 Agent、持续完成任务、积累工作经验，并在关键操作上始终保持人的控制权。**
