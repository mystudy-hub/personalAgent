# Personal Agent 本地智能体系统建设规划书

**目标版本：** V1.0 MVP  
**文档修订：** 2026-11-26  
**项目类型：** 本地优先、多 Agent 协作的个人智能体系统  
**运行环境：** Windows 11 / 本地计算机  
**核心开发工具：** OpenAI Codex  
**架构方向：** 前后端分离 + 多 Agent 调度 + 统一记忆网关 + 异步 Worker  
**建设原则：** 模块化、低耦合、可扩展、安全可控、可持续演进

首版交付一条可在 Windows 示例 Git 仓库重演的开发流程。范围见第十一章，状态与恢复见第四章，发布验收见第十五章。工作项与依赖见 [Linear 项目 pa](https://linear.app/patest/project/pa-c0340cf4fe31/overview)。

# 第一章：项目背景与建设目标

## 1.1 项目背景

随着大语言模型、Agent 工具调用和自动化开发技术的发展，传统单 Agent 模式逐渐暴露出一些问题：

1. 对话和任务执行混在一起，职责不清晰。
2. 不同任务共享上下文，容易产生记忆污染。
3. 一个 Agent 同时承担规划、执行、审查等工作，复杂度过高。
4. 长时间运行的任务容易阻塞用户交互。
5. 多个项目之间缺乏统一的知识管理和任务管理。
6. 自动执行涉及文件、代码、命令和外部服务时，缺少统一的安全控制。

因此，需要建设一套个人智能体系统，将聊天、任务调度、任务执行、长期记忆和权限管理进行解耦。

系统不以简单增加 Agent 数量为目标，而是建立一套能够长期运行、持续积累知识、管理项目并执行复杂任务的个人工作平台。

## 1.2 建设目标

建设一个以本地计算机为核心运行环境的 Personal Agent 系统，实现以下能力：

| 能力 | 建设目标 |
|---|---|
| 独立聊天 | 拥有独立人格和长期用户记忆 |
| 任务调度 | 能理解需求、拆分任务、分配执行角色 |
| 多 Agent 协作 | 多个专业 Worker 并行完成工作 |
| 长期记忆 | 统一管理用户、项目和执行记忆 |
| 项目管理 | 能理解多个 GitHub 项目的结构和进度 |
| 自动开发 | 调用 Codex 完成代码开发、测试和审查 |
| 异步执行 | 长时间任务不阻塞聊天 |
| 安全控制 | 高危操作必须经过权限检查 |
| 可观测性 | 能查看任务状态、执行日志和资源消耗 |

## 1.3 核心设计原则

### 原则一：交互与执行分离

聊天 Agent 负责与用户交流。

主 Agent 负责理解和调度任务。

Worker 负责执行具体工作。

不能让一个 Agent 同时承担全部职责。

### 原则二：Agent 不等于业务系统

Agent 负责理解、推理和决策。

任务管理服务负责任务状态。

数据库负责持久化。

工具网关负责权限。

不能将系统的可靠性完全建立在提示词约束之上。

### 原则三：记忆统一管理

所有 Agent 使用统一的记忆服务，但根据角色获得不同的记忆视图。

避免每个 Agent 独立维护一套互不相通的长期记忆。

### 原则四：先实现可靠性，再实现自主性

第一阶段不追求完全自主运行。

优先保证：

- 任务能够正确创建。
- 任务能够稳定执行。
- 任务能够中断和恢复。
- 执行过程能够追踪。
- 重要操作能够审批。
- 失败后能够定位原因。

# 第二章：总体系统架构

## 2.1 架构设计

系统采用七层架构。

1. 用户交互层
2. Agent 角色层
3. 任务编排层
4. Worker 执行层
5. 记忆管理层
6. 工具与安全层
7. 数据持久化与监控层

V1.0 的一条开发任务按以下顺序运行。各角色按授权向 Memory Gateway 读取上下文，所有工具访问经 Tool Gateway 校验；Task Manager 将每次状态变化写入 SQLite。

```text
聊天中心 → Chat Agent → 用户提交任务草稿 ─┐
任务中心直接提交 ──────────────────────┴→ Task Manager 创建任务
                         ↓
            Main Agent 提出计划 → 编排器校验依赖和角色
                         ↓
           Research → Coding（隔离工作区）→ Review
                         ↓
          审批中心展示候选 diff → 用户决定 → 工具网关复核并应用
                         ↓
          Task Manager 记录结果 → Main 汇总报告 → Chat 展示
                         ↓
              Memory Gateway 保存已验证的项目结论
```

图中的 Worker 顺序用于 CSV 验收。普通问答可直接返回，只读任务可在审查完成后交付。

## 2.2 模块职责

| 模块 | 主要职责 | 是否独立运行 |
|---|---|---|
| Chat Agent | 日常交流、人格管理、记忆查询 | 是 |
| Main Agent | 任务理解、规划、调度 | 是 |
| Task Manager | 任务创建、状态管理、重试 | 是 |
| Worker Runtime | 执行具体任务 | 是 |
| Memory Gateway | 记忆检索、写入和权限控制 | 是 |
| Tool Gateway | 统一工具调用和权限检查 | 是 |
| HITL | 高危操作审批 | 作为独立服务或模块 |
| Monitor | 日志、事件和运行状态 | 是 |

说明：这里的独立运行指逻辑和生命周期独立，不要求第一版全部部署为独立进程。

## 2.3 第一版架构约束

为了避免初期过度设计，V1.0 采用模块化单体架构。

即：

- 一个本地后台服务。
- 多个独立 Agent 配置。
- 多个可并发执行的 Worker。
- 一个统一数据库。
- 一套统一工具权限机制。

后续根据实际负载，将任务调度、Worker 和记忆服务拆分为独立进程。

# 第三章：Agent 角色体系

## 3.1 Chat Agent：聊天智能体

### 定位

负责所有日常交流，是用户与 Personal Agent 系统之间的主要沟通入口。

### 主要职责

1. 日常问答。
2. 用户需求理解。
3. 用户长期偏好管理。
4. 项目背景查询。
5. 任务进度查询。
6. 将复杂需求转交 Main Agent。
7. 将执行结果转换为用户容易理解的语言。

### 配置文件

```text
agents/chat/
├── soul.md
├── agent.md
├── permissions.yaml
└── tools.yaml
```

`soul.md` 负责：

- 人格。
- 语言风格。
- 交流方式。
- 行为原则。

`agent.md` 负责：

- 工作流程。
- 记忆调用方式。
- 任务转交规则。
- 工具调用限制。

### 权限要求

日常对话可查询任务和经授权的记忆摘要。用户明确要求保存、更正或撤回自己的偏好时，Chat 可向记忆网关提交仅限本人偏好的请求；网关鉴权、写入版本并返回回执。项目事实由第五章的写入流程维护。Chat 的工具权限排除 Shell、代码修改和文件删除。

## 3.2 Main Agent：主调度智能体

### 定位

系统的任务决策中心。

### 主要职责

1. 接收用户任务。
2. 分析任务目标。
3. 识别任务类型。
4. 查询项目记忆。
5. 制定执行计划。
6. 拆分子任务。
7. 分配 Worker。
8. 监控执行进度。
9. 处理异常。
10. 汇总执行结果。

### 任务分类

| 任务类型 | 默认 Worker |
|---|---|
| 软件开发 | Coding Worker |
| 技术研究 | Research Worker |
| 数据处理（后续） | Data Worker |
| 代码审查 | Review Worker |
| 策略研究（后续） | Quant Worker |
| 系统运维（后续候选） | DevOps Worker |

### 调度规则

简单任务直接处理。

复杂任务必须先生成执行计划。

涉及多个专业领域的任务，可以拆分成多个子任务并行执行。

涉及重要文件和外部系统变更的任务，必须经过工具权限检查。

## 3.3 Worker 专业角色

V1.0 注册 Coding、Research 和 Review 三种 Worker。Data 与 Quant 的职责保留供后续版本使用。

### Coding Worker

职责：

- 代码编写。
- Bug 修复。
- 模块重构。
- 单元测试。
- 技术实现。

执行工具：Codex。

### Research Worker

职责：

- 技术调研。
- 官方文档分析。
- 技术方案对比。
- 项目可行性分析。
- 技术报告生成。

### Data Worker

职责：

- 数据采集。
- 数据清洗。
- 数据格式转换。
- 数据质量检查。
- 数据库分析。

### Quant Worker

职责：

- 期货策略研究。
- 行情分析。
- 策略参数研究。
- 回测结果分析。
- 风险指标分析。

### Review Worker

职责：

- 代码审查。
- 逻辑漏洞检查。
- 安全性审查。
- 测试结果验证。
- 交付质量检查。

注意：第一版 Worker 应当是专业角色配置，不必为每个角色建立独立模型或独立服务。可以复用同一个模型运行环境，通过不同配置和权限实现职责隔离。

## 3.4 Worker 标准工作流程

所有 Worker 遵循统一协议：

```text
接收任务
   |
读取任务上下文
   |
检查执行权限
   |
执行任务
   |
生成执行结果
   |
运行验证
   |
提交结果
   |
等待主 Agent 验收
```

Worker 不得自行修改任务目标。

如果发现需求不明确、权限不足或执行条件不满足，必须返回阻塞状态，而不是自行猜测。

# 第四章：任务管理与调度系统

这是整个系统的核心基础设施。

不能只依赖 Main Agent 的上下文来维护任务状态。

## 4.1 任务生命周期和恢复规则

Task Manager 是状态的唯一写入者。下表中的动作由对应角色发起，经 Task Manager 校验后落库。状态、事件、版本号及当前执行尝试在同一事务更新。父任务汇总必需子任务的结果并等待自己的验收条件满足，部分成功需在报告中列出。

| 当前状态与触发 | 条件或动作 | 结果 |
|---|---|---|
| 用户提交草稿 | 按项目和提交幂等键创建任务；重复请求返回原任务 ID | `CREATED` |
| `CREATED` 开始规划 | Main 读取本任务允许的上下文 | `PLANNING` |
| `PLANNING` 收到计划 | 编排器校验角色、输入输出、无环依赖和权限；失败规则见 7.3 | 合法进入 `READY`，需补充条件进入 `BLOCKED` |
| `READY` 调度器领取 | 依赖均已成功、容量允许，原子领取并记录租约与尝试 ID | `RUNNING` |
| `RUNNING` 交付候选产物 | 记录来源、产物版本、diff 和测试证据 | `REVIEWING` |
| `REVIEWING` 完成审查 | 只读结果验收通过可交付；需修改则附原因退回 Coding；批准应用前展示审过的版本 | 分别进入 `SUCCEEDED`、`READY` 或 `WAITING_APPROVAL` |
| `WAITING_APPROVAL` 收到决定 | 有效批准后进入应用步骤；用户拒绝终止该次交付；过期或基线变化须重新核对 | 分别进入 `RUNNING`、`CANCELLED` 或 `BLOCKED` |
| `RUNNING` 完成已授权应用 | 网关核实实际写入并记录回执；必要步骤全部通过 | `SUCCEEDED` |
| 可执行步骤遇到故障 | 可安全重试则在配置上限内新建尝试；条件缺失或副作用不明记录核对项；确定失败且重试耗尽则保留证据 | `READY`、`BLOCKED` 或 `FAILED`；规划阶段重试回到 `PLANNING` |
| `BLOCKED` 条件解除 | 保存解除原因，按检查点回到规划、审查、审批或执行队列；产生新 diff 须重审 | `PLANNING`、`REVIEWING`、`WAITING_APPROVAL` 或 `READY` |
| 用户请求暂停或继续 | 尚未领取的步骤立即暂停；正在执行的步骤先保存请求，在安全边界落检查点。继续时重新检查依赖、基线和审批有效期 | `PAUSED` 并保存恢复位置；继续后从相应检查点调度。终态优先于迟到的暂停请求 |
| 用户取消非终态任务 | 停止后续调度，撤销尚未消费的批准，通知执行器终止。先核对已经开始的外部操作 | 可确认停止后进入 `CANCELLED`，结果不明进入 `BLOCKED`；核对后若取消仍有效则进入 `CANCELLED` |
| 服务重启或租约过期 | 读取最后的检查点、操作回执和待审批记录；旧租约的 Worker 无权再提交结果 | 等待审批、暂停状态保留；安全步骤重新排队；外部写入结果不明进入 `BLOCKED` |

**取消与完成竞争。** 状态更新须匹配当前版本和执行尝试。已提交的成功结果保留，晚到的取消返回实际终态；先被接受的取消阻止后续步骤。若写入已发生，在报告中记录实际改动和取消时点。终态保存为历史，人工重新发起时关联原任务。

**核对外部写入。** 网关在应用前记录操作 ID、基线和候选 diff 摘要。若进程在目标文件写入后、回执入库前停止，恢复时按记录核对目标内容。确认已应用则补记回执；确认未应用且原授权、基线仍有效才可继续；部分应用或无法判定则保持阻塞并展示差异。

## 4.2 任务数据结构

每个任务必须具有唯一 ID。

建议字段：

```json
{
  "task_id": "TASK-2026-000001",
  "parent_task_id": null,
  "title": "修复示例仓库的 CSV 空行处理",

  "priority": "normal",
  "status": "READY",
  "assigned_worker": "coding_worker",
  "project_id": "csv-demo",
  "created_at": "",
  "updated_at": "",
  "deadline": null,
  "input": {},
  "expected_output": [],
  "constraints": [],
  "result": null,
  "error": null
}
```

## 4.3 任务拆解机制

Main Agent 应当遵循以下原则：

1. 明确最终目标。
2. 确定任务依赖关系。
3. 将任务拆成可独立执行的工作单元。
4. 确认每个子任务的输入和输出。
5. 识别可并行任务。
6. 识别必须串行执行的任务。
7. 确定最终验收条件。

例如：

后续量化场景的拆解示例：升级中国商品期货量化项目的数据模块。首版 CSV 验收的角色分工见第十五章。

```text
主任务
  |
  +-- 检查现有数据源
  |
  +-- 检查数据库结构
  |
  +-- 检查数据质量
  |
  +-- 制定改进方案
           |
           v
       Coding Worker
           |
           v
       Review Worker
           |
           v
       测试与验收
```

## 4.4 异步任务管理

必须支持：

- 多任务并行。
- 任务优先级。
- 超时控制。
- 失败重试。
- 手动取消。
- 断点恢复。
- 任务依赖。
- 执行进度上报。

V1.0 优先使用数据库任务表和后台执行队列。

不急于引入复杂消息中间件。

# 第五章：统一记忆管理系统

## 5.1 设计目标

建立统一的记忆网关，避免不同 Agent 各自保存重复、冲突和过时的信息。

记忆系统应当解决：

1. 用户信息如何保存。
2. 项目知识如何保存。
3. 执行结果如何保存。
4. 记忆如何检索。
5. 记忆如何更新。
6. 记忆冲突如何处理。
7. 不同 Agent 如何获得不同记忆权限。

## 5.2 记忆分类

建议划分五种记忆。

| 类型 | 内容 | 示例 |
|---|---|---|
| User Memory | 用户长期偏好 | 使用 Windows、偏好技术方案先规划后实施 |
| Project Memory | 项目长期信息 | 项目架构、技术选型、开发进度 |
| Technical Memory | 技术知识 | 接口规范、设计方案、常见问题 |
| Execution Memory | 执行记录 | 任务结果、错误、测试报告 |
| Session Memory | 当前会话信息 | 当前需求和临时上下文 |

## 5.3 记忆存储结构

建议采用：

- SQLite：结构化记忆和元数据。
- Markdown：人类可读的项目知识。
- 首版使用 SQLite 按项目、关键词和标签检索。后续可从已授权、未归档的记录重建向量索引。
- 原始文件：完整报告、日志和证据。

不建议第一版就建设复杂知识图谱。

先把记忆的分类、更新、检索和权限做好。

## 5.4 记忆网关接口

建议统一接口：

```text
POST /api/memory/search
POST /api/memory/write
POST /api/memory/update
POST /api/memory/archive
GET  /api/memory/{id}
GET  /api/memory/project/{project_id}
```

其中：

`search`：根据 Agent 身份和任务检索相关记忆。

`write`：写入新记忆。

`update`：更新已有记忆。

`archive`：归档过期记忆。

## 5.5 记忆写入规则

记忆写入必须具备：

- 来源。
- 创建时间。
- 适用项目。
- 可信度。
- 版本。
- 状态。
- 更新记录。

特别是项目记忆，需要明确区分：

- 已确认事实。
- 当前设计方案。
- 待验证假设。
- 已废弃方案。

不能将 Worker 的推测直接作为已确认事实保存。

## 5.6 记忆权限隔离与数据使用

| 数据 | 读取和写入规则 | 模型调用可用内容 |
|---|---|---|
| 会话与用户偏好 | 会话和版本记录保存在本机 SQLite。Chat 可读取本人授权摘要；用户明确表达保存、更正或撤回意图后，由网关写入、替代或归档相应版本 | 按本次用途提供相关偏好和必要的会话片段 |
| 项目记忆、源码和 diff | Main 限当前授权项目；Worker 限任务用途、项目和所需文件。经审查的事实必须带任务 ID、证据和来源，待验证内容单独标记 | 为项目配置允许的模型服务及数据类别，仅发授权片段；未配置源码或 diff 外发授权时，需该数据的远程步骤转为阻塞 |
| 测试、日志和附件 | 完整产物保存在本机，报告引用产物位置。先做项目范围过滤，再检索或排名 | 发送获准的错误摘要或测试摘录。凭证、令牌和命中的敏感字段在请求及应用日志中剔除 |

网关使用服务端确定的用户、项目和任务身份。窗口中打开的项目、模型生成的项目 ID、检索词均不授予访问权。相同数据边界适用于 Chat/Main 的模型请求以及 Codex 可读取的输入工作区。

**偏好验收。** 用户说“以后用中文回复”，Chat 提交偏好请求，收到网关回执后再确认保存。新会话读取生效版本。用户更正为“以后用英文回复”后，新会话使用更新值；撤回后归档的记录不参与默认检索。另一项目 Worker 仅能看到当前任务获准的内容。

# 第六章：工具执行与安全控制

## 6.1 统一工具网关

所有 Worker 不应直接无限制地调用系统资源。

统一工具网关负责：

1. 身份验证。
2. 工具权限检查。
3. 参数校验。
4. 操作风险分类。
5. 审批检查。
6. 执行记录。
7. 结果返回。

## 6.2 工具分类

| 工具类型 | 示例 |
|---|---|
| 文件工具 | 读取、搜索、修改文件 |
| 开发工具 | Git、Python、Codex |
| 代码平台 | GitHub API |
| 网络工具 | HTTP、搜索接口 |
| 数据工具 | SQLite、CSV、行情接口 |
| 系统工具 | PowerShell、系统命令 |

## 6.3 权限分级

建议采用四级权限：

| 等级 | 类型 | 操作策略 |
|---|---|---|
| P0 | 只读 | 在本次授权项目和数据范围内允许 |
| P1 | 普通写入 | 按项目授权 |
| P2 | 重要变更 | 人工确认 |
| P3 | 高危操作 | 强制审批 |

典型操作：

| 操作 | 等级 |
|---|---|
| 读取项目文件 | P0 |
| 查询 GitHub 仓库 | P0 |
| 创建临时文件 | P1 |
| 在隔离工作区生成候选补丁 | P1，限本任务 |
| 将已审查补丁应用到用户项目 | P2，批准具体 diff |
| 提交到用户项目的 Git 分支 | P2，按操作独立授权 |
| Git Push | P2 |
| 删除重要文件 | P3 |
| 修改系统配置 | P3 |
| 生产环境部署 | P3 |

## 6.4 HITL 人工审批机制

1. **生成候选。** 工具网关为任务准备隔离目录和准许读取的输入，记录源项目、基线和执行身份。Coding 可以在该目录改动并运行测试。Worker 进程的文件、命令、网络和凭证权限须能实际限制它触及用户仓库或远端。
2. **审查候选。** Review 核对基线、实际 diff、测试命令及结果。将审查结论绑定至候选内容摘要。证据不足或测试失败时，退回 Coding 并保留每次尝试的记录。
3. **展示决定。** 审批页显示项目、分支、文件差异、风险、目标操作、参数、有效期和拒绝后果。每项批准绑定操作 ID、任务、执行身份、基线和候选版本。记录审批人、决定和时间。
4. **执行前复核。** 网关检查审批、当前分支、工作区现有改动及目标文件前置条件，再消费该操作的批准并执行。候选变化重新审查，目标变化重新计算差异并申请批准。拒绝或过期的操作不能写入。重复提交查询原操作回执。
5. **交付与审计。** 应用补丁、Git commit 和 Git push 使用独立操作记录及授权。默认 CSV 演练做到已批准的本地应用；只有实际执行且回读成功时，才在报告中登记提交 SHA 或推送的远端分支。中断恢复按 4.1 核对副作用。

## 6.5 审计日志

所有重要操作必须记录：

```text
操作时间
任务 ID
Agent ID
Worker ID
工具名称
经脱敏的操作参数、目标基线和候选摘要
审批记录
执行结果
错误信息
```

## 7.2 Codex 集成

Codex 是整个系统重要的开发执行引擎。

建议采用独立适配层：

```text
Agent Runtime
      |
Codex Adapter
      |
Codex CLI / Supported Runtime
      |
任务隔离工作目录
```

Codex Adapter 负责：

- 启动执行任务。
- 传递任务描述。
- 指定工作目录。
- 配置执行权限。
- 获取运行状态。
- 收集执行结果。
- 处理中断和超时。

不应将 Codex 的内部配置与 Main Agent 的业务调度逻辑混在一起。

需要先验证当前 Codex 版本支持的调用方式、认证模式和权限参数。

## 7.3 对话、规划与执行的模型调用约定

| 调用者 | 输入与输出 | 失败时对用户可见的结果 |
|---|---|---|
| Chat | 使用已配置的模型适配器。输入限当前消息、必要历史及授权摘要；输出为普通答复或可编辑任务草稿。用户提交后由 Task Manager 分配任务 ID | 认证、配额或网络故障显示可重试原因；重复提交同一草稿返回同一任务 |
| Main | 读取任务 ID、目标、项目约束及可用角色，输出结构化计划。每个节点含唯一 ID、角色、输入、预期产物、依赖和验收条件 | 编排器拒收未知角色、依赖环、缺失验收条件和越权动作。带原因返回 Main 修正一次；仍无效则进入 `BLOCKED`，界面展示节点及待补充项 |
| Worker | Research 提交有来源的发现；Coding 经 Codex 适配器输出候选 diff 和测试产物；Review 提交审查结论及证据引用。每步记录尝试 ID 和执行结果 | 可重试故障受次数上限约束。权限或资料不足返回阻塞原因，错误及进程退出信息记入任务事件 |

M0 分别验证 Chat 的一次真实问答、Main 的一次结构化计划以及 Codex 的一次只读执行。记录所用提供方、调用方式和失败表现；认证记录只写方式与结果。每次模型调用先执行 5.6 的数据检查。

2. 是否能绕过工具网关。
3. 是否存在路径穿越。

## 12.3 稳定性测试

测试：

- 后台任务运行数小时。
- Worker 异常退出。
- 服务重启。
- 数据库异常。
- 模型接口超时。
- 重复提交任务。
- 并发任务竞争。
- 审批过程中服务重启。

必须保证任务状态和执行记录不会因普通服务重启而丢失。下列场景用临时仓库和可控的模拟执行器复现；每次记录任务 ID、尝试 ID、事件序列、审批状态和目标仓库差异。

| 演练 | 注入时点 | 可复核的预期结果 |
|---|---|---|
| 暂停后恢复 | 正在运行的节点收到暂停，请求后重启服务 | 明确展示请求与生效时点；下一个节点未被领取；从已记录检查点继续，已完成步骤不重复 |
| 审查退回 | 候选测试失败或证据缺失 | 审查原因可见；新尝试产生新候选；仅新版本可被批准应用 |
| 取消与完成竞争 | 分别让完成、取消先取得任务版本 | 仅接受有效状态转换；晚到请求取得实际结果，无后续节点抢跑 |
| 审批期间重启 | 审批申请落库后、用户决定前 | 重启仍等待原请求；批准、拒绝、过期和重复请求有可追溯结果 |
| 写入后回执丢失 | 目标写入之后、成功回执入库之前 | 读取操作 ID、基线及目标内容；已应用时补回执，部分应用时进入阻塞，均不盲目重放 |

# 第十五章：发布验收与后续综合场景

## 15.1 V1.0 发布验收：修复 CSV 导入空行

**前置条件。** 使用 PAT-6 的独立 Git 示例仓库。样例含表头、两条有效记录和中间的空白行。此处空白行指两条记录之间没有字符的空行。预期返回两条有效记录，同时保留无空行输入的既有行为。带分隔符的空字段和引号内跨行内容沿用原解析规则。记录起始提交、相关工作区文件状态和修复前失败的测试。每条分支用同一基线的独立副本。

1. 用户在聊天中心输入“修复 CSV 导入遇到空行的问题，运行测试，给我看改动”。提交草稿后得到唯一任务 ID。
2. Main 生成 Research → Coding → Review 计划。Research 定位导入逻辑、失败样例与证据；Coding 在隔离目录完成修改并运行测试；Review 对同一候选版本核对 diff、失败基线和修复后测试。
3. 审批中心显示源项目、目标、基线、候选 diff 和测试证据。此时对照起始快照，用户仓库内容应一致。
4. 用户批准后，网关复核目标状态并应用。将目标仓库实际差异与已批准候选逐项核对，在目标目录重新运行约定回归测试。
5. 报告列出任务目标、原因、文件清单、测试命令及结果、未解决问题、审批决定、本地提交与远端推送状态。Memory Gateway 将有证据的项目结论关联到任务；新会话可查回结论及来源。

| 单独重演的分支 | 通过条件 |
|---|---|
| 用户拒绝或审批过期 | 目标仓库保持起始状态；拒绝记录或过期原因可查，候选 diff 留供查看 |
| 审批后候选或目标发生变化 | 原批准不能覆盖新内容；展示最新差异，候选变化须重审，基线变化后对重新核对的版本申请批准 |
| 审批或写入中服务重启 | 按 12.3 留存恢复前后事件和仓库证据；无重复操作 |
| 未请求提交或推送 | 报告明确显示各操作的实际状态，不以候选产物或模型回复推断发布成功 |

## 15.2 扩展验收：期货量化项目的数据质量

接入 Data Worker 与已授权的数据源后，保留原场景：“检查我的中国商品期货量化项目，分析当前数据质量，找出问题并完成下一阶段开发。” Main 查询项目记忆并拆分任务；Research 查数据源，Data 验证质量，Coding 在隔离目录修订，Review 核验证据。凡需改变用户项目或远端的动作均按第六章先授权再执行。报告汇总问题、修复、测试和后续决定。

# 第十六章：建设建议与最终决策

## 16.1 建设策略

建议采用：

**本地优先、单机部署、模块化架构、渐进式扩展。**

第一版不需要 Kubernetes、复杂微服务或大型消息队列。

重点是先打通：

用户交互 → 任务调度 → Worker 经工具网关生成候选 → 审查与批准 → 应用与报告 → 记忆更新。

## 16.2 建设优先级

1. 先验证模型入口和本机环境，建立可复现的 CSV 基线，然后交付能恢复的任务系统。
2. 实现角色协议和工具权限，在审批流程可验证后接入真实 Codex 写入，完成首个端到端任务。
3. 将记忆权限、前端进度和报告接入同一任务记录，按第十五章验收发布。

## 16.3 最终建设目标

最终形成一个以用户为中心的本地 Personal Agent 系统：

- Chat Agent 是个人助手。
- Main Agent 是项目负责人。
- Worker 是专业执行团队。
- Memory Gateway 是长期知识库。
- Task Manager 是任务管理中心。
- Tool Gateway 是执行控制中心。
- HITL 是安全审批机制。

**核心理念：让 AI 不只是回答问题，而是能够理解长期目标、组织专业 Agent、持续完成任务、积累工作经验，并在关键操作上始终保持人的控制权。**
